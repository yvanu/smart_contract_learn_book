## 第一组：钱包、账户、交易（最容易混淆）

### 1. EOA 和合约账户有什么不同？

**通俗说法：** EOA 可以理解为“有密钥的用户账户”，合约账户则对应一份部署好的程序与它保存的状态。

**技术解释：** 传统 EOA 主要由私钥签名发起交易；合约账户由链上代码控制其行为。智能账户等新机制让实际账户模型更加丰富，初学时先掌握这两类最常见概念。

**常见误区：** “合约账户必须有人登录才能执行”不正确。合约通常在收到外部交易或其他合约的调用时执行，本身不能像 Celery 一样自行定时运行。

练习入口：[从钱包和账户开始](/00-start/)。

### 2. 钱包里真的存着 ETH 吗？

不是。链上状态记录账户资产，钱包管理密钥、查看余额和发起签名请求。卸载钱包不会清空链上资产，但丢失唯一的密钥恢复方式可能导致无法再控制资产。

**一句话复述：** 钱包是查看和控制链上账户的工具，不是放钱的硬盘文件夹。

### 3. 为什么链上写入要消耗 Gas？

因为区块链执行和保存状态需要网络参与者投入资源，需要计量和限制滥用。Gas 是资源计量；ETH 是支付资产，它们不是同一个单位。

**类比：** 你运行 Flask 需要服务器资源；在以太坊中，执行交易需要按网络的收费规则付费。

### 4. 拿到交易哈希，是不是说明付款成功？

不是。**签名、广播、被网络接收、进入区块、执行成功、满足业务确认要求**是不同的步骤。

一个后端服务通常需要进一步查交易回执的执行状态、校验目标网络和合约，并按风险决定等待多少确认。链重组也应纳入业务设计。

练习入口：[交易、EVM 与 Gas](/02-evm/)。

## 第二组：Solidity 语法与数据（必须亲手做过）

### 5. public、private、external 分别是什么意思？

- `public`：对状态变量通常生成公开 getter；公开函数可被外部调用。
- `private`：限制在声明它的合约中进行 Solidity 代码层面的直接访问，**不表示数据加密**。
- `external`：函数面向合约外部调用，区别于内部直接调用语义。

**常见误区：** `owner` 声明成 public，并不会让所有人都可以修改它；也不会自动阻止普通用户调用其他没有加权限的函数。

### 6. view、pure、payable 有何区别？

- `view`：函数不能修改链上状态，可读取合约状态。
- `pure`：不能读也不能修改合约状态。
- `payable`：函数允许随调用携带原生资产。

例如 Counter 的 `count()` 是只读 getter；`increase()` 负责修改状态。`payable` 不等于安全收款，还需要考虑提款权限与失败模式。

练习入口：[Solidity 变量和函数](/01-solidity/)。

### 7. storage、memory、calldata 是什么？

**记忆方式：** storage 像持久柜子，memory 像一次调用用的草稿纸，calldata 像调用时带来的只读入参。

更精确地说：它们是 Solidity 的数据位置概念。修改 `storage` 引用指向的结构体字段会影响链上状态；`memory` 是临时数据；`calldata` 通常用于外部调用的只读参数。

### 8. mapping 为什么不能像 Python dict 一样列出所有 key？

Solidity mapping 没有直接暴露可枚举键集合的机制。你可以按某个 key 查询，但要显示所有用户，通常需要设计额外列表或使用事件加链下索引。

**常见误区：** 不能把 mapping 当成 MySQL 表并写“遍历所有用户”的无限循环，不受限循环可能使交易耗尽 Gas。

练习入口：[数据存储与事件](/01-solidity/storage-events)。

## 第三组：权限与安全（必须知道反面案例）

### 9. msg.sender 和 tx.origin 有何不同？

`msg.sender` 是当前这一层函数调用的**直接调用者**。用户直接调用 B 时是用户地址；用户调用 A、A 再调用 B 时，B 看到的 `msg.sender` 是 A。

`tx.origin` 代表交易最初的外部账户。把它简单当权限判断依据，可能在复杂调用链里产生安全问题。

练习入口：[从 Flask 迁移到合约](/00-start/backend-map)。

### 10. revert 会让失败交易完全免费吗？

不会。`revert` 会撤销本次 EVM 交易内已经做的链上状态更新及对应日志效果，但执行耗掉的 Gas 一般不能完全退回。

**特殊情况：** 如果本地模拟提前发现失败，客户端可能根本没广播正式交易；不要把所有弹窗错误都当成链上失败交易。

### 11. 什么是重入攻击？

一个合约调用不可信外部合约时，对方可能在原函数结束前再次调用回来。如果原合约还没更新“已付款/余额归零”的状态，攻击者可能利用旧状态走重复路径。

**防范思路：** Checks → Effects → Interactions（CEI），先检查，先更新内部状态，最后调用外部合约。但复杂跨函数/跨合约风险还需要额外分析。

练习入口：[重入风险与 CEI](/04-security/)。

### 12. 为什么“只有 owner 才能调用”还不等于安全？

因为 owner 私钥也可能被盗，收款地址也可能拒收，资金可能因业务规则卡住。安全不仅是权限检查，还包括资产去向、失败恢复、时间边界、外部依赖和用户恶意行为。

## 第四组：工程、代币与综合项目

### 13. ABI、字节码、合约地址是什么关系？

- **Solidity 源码**：开发者写的程序。
- **字节码 Bytecode**：编译后由 EVM 执行的代码。
- **ABI**：描述外部可调用函数和事件的接口信息。
- **合约地址**：定位某个已部署合约实例的链上地址。

**容易混淆：** 只有 ABI 不能唯一确定实际调用哪个合约；还需要网络和合约地址。

练习入口：[ABI 与调用](/02-evm/abi)。

### 14. ERC-20 里的 approve 和 transferFrom 有何区别？

`approve` 是设置某个 spender 可以使用多少额度；`transferFrom` 是被授权方按代币合约规则实际发起代币转移。

“授权成功”不等于“已经转账”。给陌生 DApp 无限授权可能带来资产风险。

练习入口：[ERC-20 基础](/04-security/erc20)。

### 15. Escrow 项目有哪些不能用真钱的原因？

至少指出以下三点：

1. **没有现实世界交付证明和争议仲裁**：买家可能收到货却在到期时退款。
2. **收款方拒收会导致 release 失败**：钱不会凭空消失，但业务可能卡住。
3. **缺少生产级设计与专业安全审计**：密钥恢复、风险管理、升级与监控均未完善。

不能用“我自己写了 10 多条测试”就宣称已经通过安全审计。

练习入口：[Escrow 全部源码](/05-project/escrow) · [测试与验收](/05-project/acceptance)。

## 一份五分钟自我介绍的参考组织方式

不要照着术语念，把内容讲成一次真实开发过程：

> 我做了一个本地测试用的 ETH 托管合约。先把买家、卖家以及 Funded、Delivered、Released、Refunded 四个状态定义清楚，再用 Solidity 限制每一步的权限。写转账函数时遵守先修改状态、再向外部地址转账的顺序，以降低典型重入风险。随后使用 Foundry 模拟买家、卖家和陌生人，验证越权、提前退款、重复结算、收款方拒收等场景。项目没有争议仲裁和专业审计，因此只能用于学习与测试环境。

自己试着把这段讲给不懂区块链的朋友听；对方如果问“Gas 是什么”，你还能举出一个生活例子，就说明你不是单纯背诵。
