# 00-3 从 Flask 和数据库走进链上世界

> **本课目标**：不是重新学习后端，而是弄清楚哪些后端经验能复用、哪些思维必须改变。建议先做完 [Remix 第一个合约](/00-start/environment)。

## 从一个你熟悉的订单 API 开始

你在 Flask 中可能写过这样的业务：

```python
@app.post("/orders/<order_id>/release")
def release(order_id):
    user_id = current_user.id
    order = load_order(order_id)
    if order.buyer_id != user_id:
        return {"error": "forbidden"}, 403
    if order.status != "DELIVERED":
        return {"error": "wrong status"}, 409
    order.status = "RELEASED"
    db.commit()
    return {"ok": True}
```

这段是**讲解用伪业务代码**，省略了事务与转账失败处理。它表达了一个熟悉的流程：身份验证 → 状态验证 → 修改状态。

换成合约，关键问题变成：

1. **谁来证明自己是买家？** 调用者地址，而不是 Flask 传入的 user_id。
2. **状态存在哪里？** 合约的链上持久状态，而不是你的 MySQL 表。
3. **谁能改状态？** 合约编写的权限和状态条件，不是前端按钮是否隐藏。
4. **失败怎么办？** 合约可以 revert 回滚本次链上交易的状态修改，但仍要关注 Gas 和链外流程。

一个贴近 Solidity 的简化写法：

```solidity
// 这是函数内部的演示片段，不是可以单独编译的合约
if (msg.sender != buyer) revert Unauthorized();
if (state != State.Delivered) revert InvalidState();
state = State.Released;
```

`msg.sender` 可以暂时理解为**当前这一层合约调用者的地址**。它并不保证调用者是现实世界的某个人。

## 一张对照表：熟悉的东西，不熟悉的代价

| Flask / 数据库 | 链上合约 | 需要额外注意 |
| --- | --- | --- |
| `@app.post` | 外部可调用函数 | 写入通常需要签名交易 |
| `current_user.id` | `msg.sender` | 地址不是实名身份 |
| MySQL 数据行 | 状态变量、`mapping` | 没有任意 SQL 和免费全表扫描 |
| `db.commit()` | 成功执行链上交易 | 要查回执，不只看交易哈希 |
| `raise Exception` | `revert` | 链上状态回滚，已消耗 Gas 通常不退 |
| 应用日志 | `event` | 事件供外部看，合约不能像查表一样查旧日志 |
| cron / Celery | 外部账户、自动化服务发起交易 | 合约不会自己定时醒来 |
| 服务升级 | 部署新合约或事先设计升级机制 | 现有不可升级合约不能随意热更新 |

## 最容易踩的五个坑

### 坑 1：前端禁用按钮不是权限

只在页面上判断“是不是管理员”不够。用户可以不打开网页，直接向合约发送交易。权限必须写在合约里。

### 坑 2：private 不是加密

你在 Python 类里写 `_password` 或数据库里给字段加权限，仍可以依赖服务器隔离；链上数据通常对观察者公开。Solidity 的 `private` 只限制其他合约源码直接访问该变量。

### 坑 3：mapping 不是 SQL 表

`mapping(address => uint256) balances` 很像 Python 字典，但合约不能天然枚举所有 key。若想展示“全部用户余额”，通常需要事件索引或专门维护列表，并评估 Gas 成本。

### 坑 4：链上交易回滚，链外动作不自动回滚

合约内的状态变化可以原子回滚；但你事先发出的短信、第三方支付或物流操作不属于那笔 EVM 交易。

例如：后端看见交易哈希就通知发货，随后链上交易失败，短信不会自动撤回。正确的集成方案要等待合适的链上确认并做幂等处理。

### 坑 5：msg.sender 不总是最终用户

如果用户直接调用合约 B，B 看见的 `msg.sender` 是用户地址；如果用户调用合约 A，再由 A 调用 B，B 看见的是 **A 合约地址**。

```text
用户 0xUser ───直接调用───> B
                             B.msg.sender = 0xUser

用户 0xUser ───调用───> A ───调用───> B
                                          B.msg.sender = A 的地址
```

所以不要简单地把 `tx.origin` 当作“真实登录用户”用来做授权；跨合约调用、代理、智能钱包需要明确的权限设计。

## 一笔订单为什么不能靠定时函数自动退款？

在 Flask 里你可以启动 Celery 定时扫描超时订单；但链上合约**不会因为区块时间到了，就自动执行一段代码**。合约可以检查 `block.timestamp` 是否到期，却仍需要有人（用户、机器人、自动化服务）发一笔交易触发退款。

这点对设计产品很重要：**条件满足 ≠ 操作已经发生**。

## 小练习：设计一份链上权限表

假设一笔托管订单有买家 A、卖家 B、陌生人 C。

| 操作 | A 买家 | B 卖家 | C 陌生人 |
| --- | --- | --- | --- |
| 查看订单状态 | 可以 | 可以 | 可以 |
| 标记已交付 | 不可以 | 可以 | 不可以 |
| 确认放款 | 可以 | 不可以 | 不可以 |
| 到期退款 | 可以 | 不可以 | 不可以 |

写出这样的规则，仅靠网页按钮足够吗？**答案：不够，合约必须自己检查调用者地址和当前状态。**

## 本课验收

能解释这四句话就过关：链上地址不同于 Flask 用户 ID；链上 `private` 不保密；到期不意味着自动执行；交易成功要看实际执行状态。
