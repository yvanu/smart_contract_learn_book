# 04-2 威胁建模：谁能破坏你的合约？从五个问题开始

> **本课目标**：学会在写代码前就问“谁可能故意不按正常流程操作”。不需要先掌握所有密码学知识。

## 从 Escrow 资金托管业务开始

一笔订单有：买家、卖家、资金、交付状态、截止时间。如果你只按“好人都按按钮”的流程设计，就会漏掉现实问题：

- 买家已经收到货，却拖到截止时间要求退款。
- 卖家提供一个拒绝收 ETH 的合约地址。
- 陌生人尝试替买家点击“确认放款”。
- 交易失败了，但后端按交易哈希提前记了“成功”。
- 买家或卖家账号私钥泄露。

这些都不需要复杂黑客工具，但会影响安全性和真实业务。

## 用五个问题画出第一张威胁表

| 问题 | Escrow 的答案 |
| --- | --- |
| **保护什么？** | 买家存入的 ETH、订单状态、买卖双方权限 |
| **谁可以操作？** | 买家、卖家，及任何能发交易的陌生地址 |
| **哪些操作危险？** | release、refund、转移资产、修改关键配置 |
| **谁可以故意作恶？** | 买家、卖家、第三方合约、失窃密钥控制者 |
| **失败后会怎样？** | 资金卡死、错误转账、重复结算、状态与链下系统不一致 |

## 重点 1：msg.sender 和 tx.origin 不一样

`msg.sender` 是当前合约函数**直接调用者**。如果用户直接调用合约 B，它就是用户地址；如果用户先调用合约 A，再由 A 调用 B，B 的 `msg.sender` 就是合约 A。

`tx.origin` 表示这笔交易最初的外部账户。把它直接当作通用权限凭据，可能带来钓鱼式调用链风险。初学者先记住：**按明确的授权模型判断当前调用者，不要通过 tx.origin“猜登录用户”。**

## 重点 2：签名不是“只要签了就永远可信”

假设你做一个“用户离线签名同意领取”的功能。攻击者若复制那份签名，能不能重复使用？

为降低重放风险，系统往往需要：

- **nonce**：每次授权使用独立编号，已用过就不能再用。
- **chainId**：绑定到正确的网络。
- **合约域/验证合约**：别把给 A 合约的授权拿去 B 合约用。
- **deadline**：授权过期时间。
- **明确消息结构**：如 EIP-712 typed data；但它本身不会自动实现防重放。

你不需要本课实现签名验证，先知道**签名的有效上下文必须被限制**。

## 重点 3：block.timestamp 不是精准闹钟

截止时间可以用 `block.timestamp` 比较，但合约不会在那一秒自己执行。你还需要外部交易触发动作，而且区块时间与现实世界墙钟时间不是严格一致的秒级调度工具。

在 Escrow 中，测试应至少覆盖：

- 时间在截止前：退款失败。
- 时间恰好到期：退款成功。
- 已经释放：无论是否到期都不可再退款。

## 重点 4：合约不能直接当 Flask 调互联网 API

Solidity 代码不能像 Python 的 `requests.get()` 一样，直接读取外部网站即时价格。如果业务依赖汇率、物流状态或天气，需要由外部系统提供数据，通常称为**预言机（Oracle）**。

引入数据源之后，还必须考虑：数据延迟、断供、来源被操纵、使用错误单位、价格异常等。

所以“链上执行规则透明”并不代表“输入的信息绝对真实”。

## 重点 5：业务作恶，不一定能靠代码阻止

教程 Escrow 用“到期允许买家退款”的规则。这是明确的代码规则，但现实中卖家可能已发货、买家却不确认。按这个规则运行，仍可能发生对卖家不公平的结果。

这不是合约编译错误，而是**产品与商业规则没有覆盖争议场景**。真实应用往往需要仲裁、证据机制、多签或其它设计。

## 给自己一张检查清单

每次写涉及资金的函数，都检查：

1. 谁能调用？是否能绕过前端直调？
2. 是否检查当前状态，阻止重复执行？
3. 有没有向不可信地址发送 ETH 或调用不可信合约？
4. 出错时钱在哪里，会不会被卡死？
5. 有没有依赖链外数据，数据出错怎么办？
6. 签名/时间/链切换/重放有没有考虑？
7. 有没有测试“恶意买家、恶意卖家、陌生人”？

## 练习：自己说出四条失败用例

- 陌生人尝试标记交付 → 必须拒绝。
- 截止前买家要求退款 → 必须拒绝。
- 已释放后买家要求退款 → 必须拒绝。
- 卖家拒绝接收 ETH → 资金不能消失，但业务可能卡住。

对照 `test/Escrow.t.sol` 寻找相应测试。**测试通过不是专业安全审计**，但能够说明某条已定义规则在测试环境下被覆盖了。
