# 03-2 Fuzz、Invariant 与调试：测试不只是写几个例子

> **本课目标**：理解单元测试、Fuzz、Invariant 的差别，运行一次本仓库的 Fuzz 测试，并掌握失败时的排查顺序。
>
> 初学时先学会**说清楚测试在证明什么**，不要因为看到术语就急着装十个工具。

## 第一层：普通单元测试

上一课写过：

```solidity
counter.increase(3);
require(counter.count() == 3, "wrong increase");
```

这只证明一种输入：**增加 3 是正确的**。但如果参数是 0、1、最大整数、很大数字呢？

这就进入第二层。

## 第二层：Fuzz —— 自动尝试大量输入

本仓库 `test/Counter.t.sol` 里有：

```solidity
function testFuzz_Increase(uint256 amount) public {
    counter.increase(amount);
    require(counter.count() == amount, "count mismatch");
}
```

你不需要自己列出 1、2、3、100、1000……Foundry 会生成多组 `uint256` 输入，并检查同一性质：**一个新计数器增加 amount 后，count 必须等于 amount**。

运行：

```bash
cd examples/foundry
forge test --match-test testFuzz_Increase -vv
```

预期：用例通过，输出里可能包含 runs 等 Fuzz 统计。本仓库配置 `fuzz = { runs = 128 }`；实际运行次数与版本、过滤设置有关，以终端结果为准。

### Fuzz 能证明所有输入都安全吗？

不能。它抽样检查一些输入和路径，不能自动保证覆盖所有可能情况。对“输入范围、前置状态、调用身份”没有设计的 Fuzz 测试，也可能漏掉核心风险。

例如如果测试只写“金额小于 10 时会成功”，却从未验证退款后第二次领取会失败，那么再多次随机测试也不能证明不会重复付款。

## 第三层：Invariant —— 无论怎样操作都必须成立的规则

假设 Escrow 合约允许：买家付款 → 卖家交付 → 买家放款，或者到期退款。

可能的不变量包括：

1. 一笔托管订单**不能既退款又放款**。
2. 进入 Released 后**不能再回到 Funded**。
3. 进入 Refunded 后**不能再放款**。
4. 非授权地址不能改变资金归属。
5. 合约状态和资金去向必须能解释，不能无缘无故“多付一笔”。

区别在于：Fuzz 常常针对某个函数的大量入参；**状态机不变量**更关注一系列操作组合后，规则是否仍成立。例如：

```text
创建订单 → 标记交付 → 退款 → 再次放款
                           ↑
                        必须阻止
```

工程中通常会编写 handler 控制动作、身份和前置条件，避免把“设计上就应该失败”的调用误当作安全漏洞。**本仓库 v0.1 有 Fuzz 用例，但完整 Invariant Handler 仍属后续工作，不应当成已实现功能。**

## 第四层：边界值，比随机输入还重要

拿一个截止时间 `deadline` 举例：

| 输入时间 | 是否允许到期退款 |
| --- | --- |
| `deadline - 1` | 不应该允许 |
| `deadline` | 应允许 |
| `deadline + 1` | 应允许 |

这叫边界测试。“差一秒”往往比测试一千个随机的普通时间更能找到错误。

但真实公链的时间戳存在协议和区块生产相关的限制，不能把它当成精确的现实世界定时器。

## 看懂 Foundry 的本地测试作弊码

| Cheatcode | 白话含义 | 用在哪里 |
| --- | --- | --- |
| `vm.prank(addr)` | 让下一次调用模拟为 addr | 测试陌生人越权 |
| `vm.expectRevert(...)` | 预期下一次调用失败 | 测试权限 / 状态错误 |
| `vm.warp(timestamp)` | 在本地测试环境改变区块时间 | 测试到期边界 |
| `vm.deal(addr, amount)` | 在本地测试给地址设置余额 | 测试付款 |
| `vm.expectEmit(...)` | 预期发出指定事件 | 验证审计日志 |

这些能力属于**本地模拟测试环境**，不是上线后某个用户真的可以修改主网时间或他人的余额。

## 出现 FAIL 怎么排查？按顺序来

1. **看名字**：哪条测试失败？是正常场景还是反向场景？
2. **看输入**：尤其 Fuzz 输出中的失败参数，是否进入了你没想到的边界？
3. **看调用者**：当前 `msg.sender` 是谁？是否被 prank 修改？
4. **看状态**：执行前是 Funded、Delivered，还是已退款？
5. **看时间与余额**：是否刚好在截止点？
6. **看错误**：期望的 revert 与实际错误是否一致？
7. **打开调用轨迹**：

```bash
forge test --match-test testRefundAfterDeadline -vvvv
```

如果这个名字在你的代码版本中不存在，先用 `forge test --list` 查看当前测试名，再替换成实际名称。

## 做一份自己的测试清单

以 Escrow 为例，不需要马上写代码，先在笔记里列出：

- 买家付款后余额应该怎样？
- 卖家未交付，买家能否放款？
- 陌生人能否标记交付？
- 截止时间前一秒能否退款？
- 截止时间恰好到达能否退款？
- 已经放款，还能再退款吗？

每一个问题都能变成一条自动化测试。
