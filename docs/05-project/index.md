# 05-1 第一个完整项目：用 Escrow 理解链上托管

> **本课目标**：先用业务语言画出一笔订单的规则、参与者、状态和失败情况，再读 Solidity 代码。不要上来就复制 100 行合约。
>
> **学习环境**：仅限本地 Foundry/Remix VM 或无价值的测试网。教程合约不支持商业仲裁，未经审计，严禁用于真实资金托管。

## 一句话解释 Escrow

Escrow 意思是**托管**。你想买一件二手商品，但不愿意直接把钱给卖家，于是将钱先放到一个按公开规则执行的托管合约里。

假设买家 A 与卖家 B 约定：

1. A 创建订单时，向托管合约存入 1 ETH 的**虚拟测试资金**。
2. B 完成交付，点击“已交付”。
3. A 确认满意后，合约释放资金给 B。
4. 如果超过截止时间仍没有正常结束，A 可以按教程规则申请退款。
5. 一笔订单只能释放一次，或退款一次，不能同时发生。

注意：这里的“交付”只是卖家主动声明，**合约自己不能确认真实快递是否签收**。所以这是教学规则，不是公平的电商仲裁产品。

## 第一步：明确角色和动作

| 角色 | 可以做什么 | 不能做什么 |
| --- | --- | --- |
| 买家 Buyer | 部署时付款、已交付后放款、到期退款、读状态 | 代替卖家标记交付 |
| 卖家 Seller | 截止前标记已交付、读状态 | 擅自从合约拿钱 |
| 陌生人 | 读公开状态 | 标记交付、放款或退款 |

所有人都可能直接向合约发交易，所以这些规则必须由合约执行。钱包地址不是实名身份，业务应用要另行解决身份与争议问题。

## 第二步：把状态写清楚

本仓库使用四种状态：

| 状态 | 中文含义 | 还可以做什么 |
| --- | --- | --- |
| `Funded` | 买家已经付款，钱在合约里 | 卖家可在截止前交付，买家可到期退款 |
| `Delivered` | 卖家已声明交付 | 买家可以放款，或按规则到期退款 |
| `Released` | 已向卖家释放 | 最终状态，不能再放款或退款 |
| `Refunded` | 已向买家退款 | 最终状态，不能再放款或退款 |

用图表示：

```text
买家创建订单并付测试 ETH
             │
             ▼
          Funded
          /    \
   卖家交付     截止后买家退款
        /        \
       ▼          ▼
   Delivered    Refunded（结束）
      /  \
买家放款   截止后买家退款
    ▼           ▼
 Released     Refunded
 （结束）       （结束）
```

这里重要的不是英文单词，而是：**哪些箭头可以走、谁能走、在什么时间能走**。不允许的箭头都应失败。

## 第三步：哪些输入部署时必须确定？

合约部署时传入：

- `seller`：卖家地址。
- `deadline`：一个未来的 Unix 时间戳（秒）。
- `msg.value`：部署交易附带的虚拟 ETH。
- `msg.sender`：自动作为买家地址。

合约还会记录当前状态为 Funded，并发出 Funded 事件。

注意：教程是一笔订单部署一个 Escrow 实例。不是使用同一份合约就自动管理全平台成千上万笔订单。这样设计是为了把角色和状态讲清楚。

## 第四步：先猜失败场景

正常流程很短，但一个合约真正需要验证的，是下面的问题：

- 卖家未交付，买家能否直接放款？**不能。**
- 陌生人能否标记交付？**不能。**
- 买家能否在截止前退款？**不能。**
- 放款之后，买家能否再次退款？**不能。**
- 收款地址拒绝接收 ETH，资金会不会“凭空消失”？**不应该；交易会回滚，但业务可能卡住。**
- 买家明明已经收到了货，到期却退款怎么办？**教程没有解决商业争议，这属于真实产品缺失的规则。**

这张清单稍后会变成 Foundry 自动化测试。

## 本课思考题

**问题：** 为什么不能只保存一个 `isPaid = true/false`，而要区分 Funded、Delivered、Released、Refunded？

<details><summary>参考答案</summary>

因为“已经付款”并不足以描述后续行为：卖家是否声明交付、资金是否已释放、是否已退款，都影响下一步谁能操作。只有一个布尔值容易让状态组合含糊，导致权限和重复结算问题。
</details>

**本课验收**：能不用看代码，向别人描述四个状态、三种角色、两条最终路径和至少三种必须失败的操作。
